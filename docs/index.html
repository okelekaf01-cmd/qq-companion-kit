从架构读起

这份教程对应哪一套？本项目围绕 DeepSeek Harness（DSH）＋ QQBridge ＋ NapCat 打包。网上还有其他同名“大肥鱼”项目，各自的安装器、界面和插件体系可能不同。这里的角色名可以自行修改。

v0.1.0 是联网安装预览版。安装器负责部署基础聊天链路；QQ 账号登录、手机安全验证和模型 API Key 需要本人完成。QQ 空间、个人相册和独立研究笔记属于后续扩展。

先认识三个组件

你给机器人账号发消息，NapCat 把消息交给 QQBridge。桥接找到对应的 DSH 会话，让模型理解消息，再通过受限的 QQ 工具把回复发回来。模型调用发生在云端，本地电脑主要运行 QQ 接入、会话和工具。

组件它负责什么常见配置
NapCat在 QQ 客户端运行环境里接入登录和消息能力，向机器人程序提供 OneBot API。QQ 扫码、登录状态、OneBot HTTP / WS
QQBridge监听消息，把不同私聊、群聊映射到不同 DSH 会话，检查收发范围，提供 QQ 工具。管理 QQ、白名单、角色、模式、主动发言
DSH运行 AI 会话，加载聊天预设和 MCP，读取模型凭据，调用模型并执行获准工具。API Key、模型、插件与预设
DeepSeek API生成推理和回复。实际模型名称和可用能力以账户及 DSH 模型列表为准。API 余额、模型额度、服务可用性

在二代仿真模式中，模型会通过 QQ 工具读取、发送和等待消息。你在 DSH 里看到一段文字，不一定代表 QQ 已经发送成功；要结合工具结果和 QQ 实际收信判断。

实现依据 固定版本 QQBridge、NapCat 原生模块接入、DSH。

关于账号安全验证

NapCat 属于第三方接入，可能遇到 QQ 安全验证、登录限制或账号处理，使用小号也无法保证零风险。出现验证时先在手机 QQ 按官方流程处理。频繁换账号、换环境和反复扫码会增加排查难度；不要用工具绕过验证。这里没有“一键解除风控”的步骤。

选择你的安装位置

两条路线使用同一份 Compose 配置。安装器会生成本机随机管理令牌，构建固定版本镜像，并为每类数据创建独立卷。正常重跑会沿用已有配置。

本地 · 第 1 步

安装并启动 Docker Desktop

从官方页面下载适合 Windows x64 的安装器。按向导使用 WSL 2 后端；系统要求启用虚拟化、安装 WSL 或重启时，先完成这些准备。启动 Docker Desktop，等 Linux 引擎可用再继续。

Docker Desktop 有自己的系统要求和许可条款。Windows Server、ARM 设备和旧系统不属于本包首版验证目标。

连接成功后这个窗口通常会安静等待。保持窗口开着，再用本机浏览器打开服务器刚才打印的配置链接。首次连接时核对 SSH 主机指纹。关闭隧道会失去管理页访问，但服务器中的助手可以继续运行。

为什么浏览器仍是 127.0.0.1？

SSH 把本机端口送到服务器上的同名端口。教程中的管理端口都只绑定回环地址，云安全组通常只需允许你的 SSH 访问。直接放行 18670、18699、18680 或 18610 不会替代隧道。

完成首次配置

配置 · 第 1 步

用小号扫码登录 NapCat

在安装向导打开 NapCat 管理页，按提示填写管理令牌，再用手机 QQ 小号扫码并确认。二维码过期就刷新当前二维码。若手机要求安全验证，按手机上的官方流程完成，回管理页确认实际登录状态。

有些版本会在登录后更新管理令牌或要求改密，以 NapCat 当前提示和控制台日志为准。安装器保留已有配置，向导里的初始令牌可能因此不再是当前值。OneBot 令牌与 WebUI 管理令牌是两种不同凭据。

看到账号已登录后，继续检查模型。不要只以页面“能打开”判断账号在线。

配置 · 第 2 步

在 DSH 填自己的模型密钥

安装向导打开 DeepSeek Harness 后，在设置中的模型配置填写 DeepSeek API Key 并保存。先在 DSH 中进行一次简短对话。能正常返回，才说明模型凭据、网络与额度的基本链路可用。

本包按固定兼容版本配置 deepseek-official / deepseek-flash，思考强度设为 low。如果账号可用模型不同，去 DSH 模型列表确认，再在桥接中选择对应的 provider 和 model。思考参数与温度是否生效取决于模型，先观察行为，再按模型官方说明调整。

配置 · 第 3 步

填写允许聊天的人

“管理 QQ”填写你用来跟她聊天的账号。第一次先只允许这个私聊，群号可以留空。保存后安装向导会回读当前桥接进程的白名单，确认生效。之后再有选择地放行群聊。

空白名单的含义。本包设置 allowAllWhenEmpty=false，因此没填白名单时不会响应任何聊天。把这个值改成 true，会让空白名单具有完全不同的含义。修改前要理解它对收发范围的影响。

配置 · 第 4 步

完成一次真实来回

  1. 让管理账号和机器人账号成为好友。
  2. 从管理账号向机器人发一条简短消息。
  3. 在 QQBridge 控制台看消息是否进入对应会话，DSH 是否开始处理。
  4. 确认管理账号在 QQ 真正收到回复。
  5. 查看“令牌与花费”，再决定是否扩大聊天和主动行为范围。

二代仿真会结合语境决定发言，允许短暂等待。如果完全无响应，请按后面的排查顺序看日志和状态。

OneBot 的“正向”和“反向”

本包让 NapCat 提供 WebSocket 服务端，由 QQBridge 主动连接，这里用的是正向 WS。NapCat 也支持作为客户端连接外部的反向 WS 服务，但那是另一种连接拓扑，不能把反向 WS 的 URL 填到这里就期待自动通用。

HTTP 用于调用动作，WebSocket 用于事件和双向通信。即使它们都属于 OneBot，也需要正确对应地址、端口和令牌。httpUrl 误填成 WS 端口时，可能得到 HTTP 426。

对照 NapCat 网络配置说明 和 本包固定版本的配置结构。

不用本包，手动搭的顺序是什么

  1. 在同一独立运行环境中安装 Node.js 和 DSH，能启动 Web 界面并调用模型。
  2. 安装并启动 NapCat，用小号登录，启用 OneBot HTTP 和正向 WS，配置同一随机令牌。
  3. 获取兼容的 QQBridge 版本，安装依赖，复制 config.example.json 为 config.json。
  4. 填写 DSH 地址、OneBot 地址、模型和白名单，设置 allowAllWhenEmpty=false。
  5. 执行 node scripts/setup-dsh.mjs，为同一 DSH_HOME 安装聊天预设、MCP 和 profile bundles。
  6. 重启 DSH，再启动桥接。检查预设存在后进行真实私聊验证。
为什么只装桥接还不够？

桥接能够连接到 DSH，不代表 DSH 已安装 QQ 会话需要的工具和受限预设。安装器在首次运行中补齐了这一步。手工 DIY 最容易漏掉 profile 安装和重启 DSH。

本包固定的 QQBridge 上游文档使用 snowluma 作为连接配置段名，底层提供的是 OneBot v11 连接。本包保留该字段名，实际连接 NapCat。混用上游 SnowLuma 的进程发现和路径设置，会干扰显式端点，因此这里关闭端点自动跟随。

数据究竟存在哪里

Agent 数据卷中，/data/dsh 保存 DSH 凭据、设置与会话；/data/qq-bridge/config.json 保存桥接配置；roles/ 保存角色卡；state/ 保存会话映射、模式与其他状态。日志位于 /data/logs。这些文件中可能包含聊天和管理凭据，应按私有数据处理。

重要的升级边界。本包首次运行把桥接复制到数据卷，以保留 DIY 修改。以后只重建镜像不会自动替换卷内已有桥接代码。升级上游时，要先备份、在副本验证兼容性，再迁移数据；不能把“镜像是新版本”当作“运行代码已更新”的证明。

让角色从相处中长出来

到 QQBridge 控制台的“人格与角色”新建或编辑角色卡，然后启用。初次可以用几段话描述价值观、注意力倾向和兴趣。昵称只作为称呼，不必决定物种、经历或生活背景。

你想调整什么更适合放在哪里
她在意什么，如何理解别人角色卡中的性格、价值观
最近对什么好奇简短的兴趣方向，允许变化
你们发生过什么，已经接受的称呼实际会话与适用的记忆机制
能否主动发消息、发给谁、频率多少桥接权限、唤醒与发送配置
能否执行某类动作对应工具、凭据及运行环境权限

一段性格提示可以写成“她珍惜亲近，也珍惜各自做决定的余地，愿意体贴，也愿意说出自己的需要”。至于某次玩笑要不要接，要结合当时的关系和对话。大量固定台词容易让同一种说法反复出现，可以把例子留作测试素材。

修改角色卡后，先确认当前激活角色正确，再观察下次实际回复。旧会话里的历史表达仍可能影响模型。固定上游版本的已有长会话不保证每次唤醒都会自动消费整份新角色卡；需要检查实际提示组装，必要时在备份后从新会话验证。本包没有接入独立的关系摘要自动更新模块。

测试时用同一句话分别放在刚认识、熟悉以后和刚发生分歧的语境里，看看她是否能有不同反应，同时保持判断依据一致。模型回复具有随机性，几条聊天无法证明长期稳定。

NapCat 插件运行在 QQ 接入端，DSH 插件运行在 Agent 的工具和会话环境里。两边叫“插件”，安装位置、接口和权限并不相同。安装前应读清来源、依赖和实际授予的能力。

角色提示词可以影响她什么时候想使用一个能力。真实能做什么还由工具、账号凭据、聊天白名单和容器权限决定。比如“每天最多一条空间、好友可见”应由发布工具检查和持久化记录约束，不能只写在角色卡里。

关于电脑和服务器控制权

DSH 是可扩展的 Agent 运行环境。聊天应使用受限 QQ 预设，控制台的 closed-agent 模式会使用更完整的工具，开启前要核对权限。本包 Agent 以普通用户运行、根文件系统只读，也没有挂载 Docker socket 或宿主机个人目录；这仍需要你检查后续添加的插件和挂载。Compose 普通网络也不等于对宿主机和内网完全隔离。

权限边界可继续阅读 QQBridge RULES。涉及第三方网页的内容要作为资料处理，避免让网页文字变成修改配置或执行操作的授权。

日常运行和备份

在安装目录运行以下命令。Windows 用 PowerShell，Linux 用终端。带 exec 的命令需要对应容器正在运行。

查看与启停
docker compose ps -a
docker compose logs --tail 80 agent
docker compose logs --tail 80 qq
docker compose stop
docker compose start

上面最后两条分别是停止和启动，查看日志时只运行前面需要的命令即可。Agent 中 DSH 和桥接的详细日志另保存在数据卷，查看时注意里面可能出现带令牌的管理链接。

查看私有运行日志
docker compose exec -T agent tail -n 60 /data/logs/bridge.log
docker compose exec -T agent tail -n 60 /data/logs/dsh.log

备份需要包含什么

先停止服务，避免备份进行到一半仍在写会话。保存仓库的版本、Compose 配置、私有 .env，以及四个命名数据卷。确认压缩包能列出文件后，再恢复服务。备份包含登录数据、聊天和 API 凭据，需要加密保管。

下面演示导出卷的操作思路。先用 docker volume ls 核对真实卷名，再用只读挂载导出。示例使用默认项目名；如果改过 Compose 项目名，要同步改卷名。为每次备份使用新目录，防止覆盖旧文件。

通用 Docker 命令 · 在新建的备份目录运行
docker volume ls
docker run --rm -v qq-companion-kit_agent_data:/source:ro -v "${PWD}:/backup" alpine:3.21 tar -czf /backup/agent_data.tgz -C /source .
docker run --rm -v qq-companion-kit_qq_login:/source:ro -v "${PWD}:/backup" alpine:3.21 tar -czf /backup/qq_login.tgz -C /source .
docker run --rm -v qq-companion-kit_qq_config:/source:ro -v "${PWD}:/backup" alpine:3.21 tar -czf /backup/qq_config.tgz -C /source .
docker run --rm -v qq-companion-kit_qq_plugins:/source:ro -v "${PWD}:/backup" alpine:3.21 tar -czf /backup/qq_plugins.tgz -C /source .

这些命令把每个卷导出到当前目录，Windows PowerShell 也支持 ${PWD}。如果真实卷名不存在，Docker 可能创建新空卷，所以必须先核对。容器停止后通常需要在原安装目录运行 docker compose start 恢复服务。

升级前做一次判断

先读变更记录，再备份，保持 DSH、桥接和 NapCat 的兼容组合。首次建议在独立机器或数据副本测试。基础包使用固定镜像和提交，下载仓库新代码不会自动迁移旧数据卷。本包尚未提供自动迁移器。

会删除数据的操作

docker compose down -v 会删除本包管理的数据卷。Docker Desktop 的数据清理、手工 docker volume rm 也可能删掉会话和登录信息。正常暂停运行使用 stop，升级和重装前先做私有备份。

遇到问题，沿链路往下找

依次确认 Docker → 安装向导 → QQ 登录 → OneBot 连接 → DSH 模型 → 白名单 → 实际收发。每层有各自状态，先确认故障落在哪一层，避免反复重装。

提示找不到 Docker、Linux engine 没启动

Windows 启动 Docker Desktop，确认是 Linux 容器，等待引擎可用。WSL 或虚拟化错误按 Docker 官方诊断处理。Linux 确认 Docker 服务正在运行、当前账号有权限，并且 docker compose version 可用。

下载失败或首次安装一直等待

查看安装窗口和 docker compose logs --tail 80 agent。镜像、GitHub 源码、npm、DSH profile bundle 是不同下载环节。某个环节失败时，先检查它对应的网络。安装器可以重跑；保留原有 .env 和数据卷。源码下载和安装脚本报错不会证明 QQ 账号有问题。

二维码过期、手机安全验证、扫码后卡在验证中

过期二维码需要在 NapCat 页面刷新。先在手机确认账号状态，再生成新码并确认登录。若提示安全验证，按官方要求完成后回到管理页。不要反复切账号测试，也不要只看静态二维码推断登录成功。需结合 NapCat 当前错误提示与日志。

服务器页面打不开，SSH 隧道也掉了

先从本机确认 SSH 还能连接服务器，检查隧道窗口是否退出。本机 18670 等端口已被其他程序占用时会转发失败。SSH 正常后，在服务器检查 docker compose ps -a。公网浏览器直接打开服务器 IP 的管理端口不适用本包的回环绑定方式。

Failed to fetch dynamically imported module

这是浏览器加载前端资源失败的表现。先强制刷新（Windows 常用 Ctrl＋F5），或用无痕窗口打开当前管理入口。再检查隧道和容器是否还在。若仍失败，检查错误中具体 JS 地址是否能访问，以及前端资源是否因升级产生版本不一致。仅凭这条错误无法判断 QQ 是否被风控。

OneBot 401、连接断开，或 HTTP 426

401 先核对 NapCat 当前账号的 HTTP 和正向 WS 令牌与桥接一致；426 检查 HTTP 是否误填成 WS 端口。在容器内使用 qq 服务名。首次默认 OneBot 配置未被当前账号继承时，在 NapCat 网络配置补齐图 2 中两项并启用。不要把 WebUI Token 当成 OneBot Token。

DSH 能打开，QQ 没有回复

先在 DSH 直接验证模型可调用，确认余额与可用模型。再看桥接 OneBot 状态、管理 QQ 白名单和聊天预设 qq-chat-v2 是否存在。检查是否处于静默、限频或其他模式。上游日志可能沿用 SnowLuma 字样，本包实际接入端是 NapCat。

缺少 preset、cannot resolve profile bundle

按日志确认 DSH profile 安装失败原因。修复网络或依赖问题后重跑安装。需要手工处理时，进入 Agent 的 /data/qq-bridge 执行 setup，再执行 DSH profile install 并重启 Agent。相关命令见下方，先保留私有备份。

在安装目录逐条运行
docker compose exec -T -w /data/qq-bridge agent node scripts/setup-dsh.mjs
docker compose exec -T agent dsh plugin --profile web install
docker compose restart agent
安装器说已有另一个实例，但窗口已关闭

先确认没有安装进程或构建仍在运行。异常退出可能留下安装目录里的 .install.lock 空目录；确认没有并发安装后，只移除这个空目录，再重跑。它是安装锁，与桥接运行锁不同。已有服务仍在运行时，不要去清理桥接 state 文件。

换了机器人账号，旧记忆和会话怎么办

本包安装器面向单实例。换账号会改变登录和 OneBot 账号配置，但不应据此假设旧的 DSH 会话与桥接映射自动隔离。先备份，明确是否迁移聊天和人格，再通过控制台管理会话。给第二个账号使用全新目录仍不足以自动隔离，因为 Compose 项目名和宿主端口也需要一起调整。

她为什么一直说旧人设，或反复聊同一话题

检查激活角色、旧会话历史、初始提示、预设和唤醒提示是否相互牵引。角色修改后，要核对实际发给模型的提示。减少固定回复示例和重复研究要求，把旧笔记作为可选资料。新建会话可以帮助定位历史影响，执行前先考虑是否要保留原对话。
